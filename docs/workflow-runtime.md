# Workflow / Organization runtime

Workflow mode is disabled by default. Settings stores a versioned, acyclic graph in ADE's private SQLite registry. A run snapshots that graph, so changing settings cannot change an active assignment. There is no hardcoded orchestrator node: the exact owned agent receiving the user's message owns the run.

## Execution and authority

`OrganizationRuntime` intercepts the normal message endpoint when enabled. Chat, card composers, and Kanban all use this endpoint. Raw terminal typing and question/approval answers are not task submissions and remain untouched. A session cannot own two active workflows, and a source checkout cannot host overlapping runs. Internal worker assignments bypass the automatic trigger.

The coordinator receives the original request and a private CLI identity path. It reads the bundled, version-matched skill, submits a participation plan, and uses fixed commands to dispatch ready nodes. A participation subset must include every predecessor. The immutable DAG is authoritative: a successor cannot dispatch before every predecessor explicitly reports `completed`. No terminal output, process exit, model turn end, heartbeat, or message wording can complete a workflow step.

Each assignment launches a detected provider in the exact discovered worktree. Its title becomes the tab title. Requested model/effort options are validated against bounded native catalogs: Codex `model/list`, Claude's `list_models` control request, and Antigravity's `models` listing. Antigravity effort choices resolve only to variants actually in the returned catalog. Requested settings never substitute for observed effective metadata.

Workers explicitly report a result once. Identical duplicate reports are idempotent; conflicting reports are refused. The coordinator consumes results, handles questions through the bounded mailbox, and explicitly finishes with a summary before returning the final answer in its normal conversation. Workers can address only the orchestrator or direct graph successors; queued messages never dispatch a successor. Shared-checkout workers are serialized and settled terminals must stop before the next writer starts.

The control endpoint accepts a private bearer identity scoped to the run, session, and terminal launch token. It accepts only fixed workflow commands, never arbitrary executable names, flags, RPC methods, terminal handles, paths, or shell input. Identities are never returned to browser clients. They are revoked on finish/cancel/shutdown; restarting a terminal invalidates its previous lease. Runtime restart marks unfinished runs failed rather than replaying possibly delivered input. Check retained work before starting another run.

This is execution-order enforcement in Vade's control plane, not an OS security sandbox. Provider processes run with the user's normal filesystem permissions and configured approval mode. The skill prohibits shell-based agent spawning and side-channel coordination; an intentionally noncompliant process cannot be contained by a prompt or a Git worktree.

## Isolated workstreams and integration

Isolation is conditional, not a worktree per node. The coordinator must identify at least two independent workstreams. A stream can contain a sequential chain. Cross-stream dependencies, shared nodes, and transitive dependencies between streams are rejected. Shared final review nodes run after integration. Work with prerequisites should remain in one stream or use the serialized shared-checkout plan.

Stream branches start at the source HEAD captured when the run begins. Workers commit their own changes and leave their checkouts clean. Integration requires every stream node's explicit success and confirmed worker teardown. Vade pins the stream commit SHAs, merges into its own integration worktree, then fast-forwards the clean, unchanged source checkout. No push, force reset, automatic abort, or destructive cleanup occurs. Conflicts leave the source untouched and retain the integration worktree for manual resolution. After resolving and committing there, the coordinator can call integrate again. If the source HEAD changed independently, integrate retained branches manually; Vade refuses to overwrite it. Worktrees remain available after completion or cancellation.

## Installation and CLI

Settings → Installation / Setup installs `resources/orchestration/vade.cjs` and `SKILL.md` into the private ADE data directory (default `~/.ade/orchestration`). Verification compares bundled hashes and checks installed Node.js. No Orca installation or network download is needed. Desktop builds include these resources and set their exact resource directory. Provider sign-in and trust prompts stay in Chat/Terminal.

Install/Update opens a private owned shell outside the project registry, stages the fixed bundled installer command once, and waits for the user's Enter. The terminal uses the existing bounded, origin-checked socket protocol and renderer acknowledgement credit. Navigating away closes that exact setup terminal; no input is replayed.

Setup installs `vade-cli` (command awareness) and `vade-orchestration` (role/dependency protocol) through the official `npx --yes skills@1.7.4 add <bundled-skills-directory> --skill vade-cli vade-orchestration --global --agent codex claude-code antigravity --yes` flow. The source is the version-matched local bundle, so unpublished changes do not depend on a nonexistent remote release. The pinned installer places both skills in `~/.agents/skills` for Codex and Antigravity and links Claude Code's skills directory. It then installs the private CLI and matching assignment guides. Setup verifies installed skill contents, rather than accepting installer output as proof. Normal agent permissions remain unchanged.

Antigravity model discovery uses the installed native `agy models` command, not an embedded model inventory. A Windows probe on 2026-10-22 returned 13 tab-separated model IDs/labels. REA inspected the native Go PE artifact (SHA-256 `d191b2e423c8c5a96ffba84699dd5f52f4eec0e74bb457e8d5f755dc55528f9d`); its process-capture adapter explicitly does not support Windows descendant cleanup, so the upstream service implementation was not verified. The observed CLI response is sufficient for the current bounded model-list integration; no guessed service endpoint is used.

Settings and history performance follow the shared-cache and bounded-background-work principles in Orca's `src/main/ai-vault/cached-session-list.ts` and `session-scanner-background.ts` (reference commit `45ee56e1a54bd032ce5bf7bda0c4bc8c9a02f307`). Vade shares agent-catalog requests for 15 seconds, invalidates them after preference changes, separates connection caches by scope, and excludes GitHub probes from provider accounts. History parsing runs at most four reads concurrently within existing file/byte budgets and yields between JSONL batches. Codex/Claude metadata is cached only for the exact session and unchanged file identity/stamps; Antigravity's separate database prevents using that transcript-only cache. Chat SSE listens to the verified transcript's directory with a 75ms debounce, filters to the exact file, retains two-second polling for missed events and unavailable watchers, and closes watchers with their streams. Terminal bytes and process liveness never become chat data.

The injected shell-specific CLI prefix uses Node.js and the exact identity file; it works even for an agent started before installation. Fixed commands are `context`, `plan`, `dispatch`, `message`, `result`, `integrate`, `finish`, `cancel`, and read-only bounded `wait`. The latter returns after a state change or at most 55 seconds. CLI timeouts never repeat mutations. A pre-write readiness refusal permits a deliberate pending dispatch after setup; uncertain delivery is never replayed. Cancel and begin a fresh run after inspecting uncertain input.

The Settings run list exposes plans, node states, explicit results, errors, and cancellation. Live topology cards identify orchestrator/worker roles and show actual dispatch/dependency edges. Provider attention/liveness remain distinct from workflow outcomes. Finishing/cancelling produces an explicit Inbox workflow result bound to the contacted agent. Kanban ignores intermediate orchestrator turn endings and settles from this final result.

## Architectural references

Implementation is standalone original Vade code informed by these source references:

- [Paperclip](https://github.com/paperclipai/paperclip/tree/043f2514e67c50320433a0013fb228a75a51325c): `skills/paperclip/SKILL.md`, `server/src/services/issues.ts`, `issue-dependency-wakeups.ts`, and `agents.ts`. Applied the distinction between hierarchy and blockers, run ownership checks, explicit results, and readiness-based wake behavior.
- [Orca](https://github.com/stablyai/orca/tree/45ee56e1a54bd032ce5bf7bda0c4bc8c9a02f307): `skill-guides/orchestration.md`, coordinator-loop/worker-contract references, provider catalog probes, and CLI orchestration sources. Applied run/assignment authority, explicit result reporting, bounded waiting, exact provider binding, and version-matched skill discovery. Native model probe wire formats follow the provider protocols documented by those implementations; no Orca runtime code or service is required.

An initial orchestrator send rejected before any terminal input ends that workflow as Failed and releases its lease. A typed `UncertainMessageDelivery` from partially staged input remains Blocked and is never retried automatically. Old runtime leases are still revoked on restart. Nonisolated workflow sends do not require HEAD; isolated workflows require a verified initial commit.
